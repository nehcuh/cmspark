# Review: UI Mode P0+P1 Implementation

## Verdict
**APPROVE_WITH_FIXES**

## Summary

The implementation faithfully encodes the approved three-mode ontology (L0/L1/L2) with correct derivation logic, hysteresis, pin semantics, and badge/toast signalling. The SafetyStrip/MinimalConfirm content-split correctly relocates heavy confirmation to Cockpit while preserving mandatory abort in Panel. The Cockpit itself delivers dual-track, ConfirmElevated, task dock, and conductor input as specified. However, three concrete security-implementation gaps must be closed before human product confirmation: (1) Cockpit ConfirmElevated nonce anti-paste is weaker than Panel's — keyboard paste vectors (Ctrl+V/Cmd+V) are unblocked; (2) `openOrFocusCockpit` has no concurrency lock, risking duplicate windows under rapid companion events; (3) Panel's full `SecurityConfirmationDialog` has no timeout, violating D14. The dual-store architecture, follow-up queue (visual-only), and missing thread-trust in Cockpit are honest limitations acceptable for P1. With the three must-fix items resolved, the branch is shippable.

## Answers to §4

### Q1 — Does P0 ModeController correctly encode L0/L1/L2 + pin + hysteresis vs the approved design (including dual-review amendments D9′–D16)?

**Yes, with one notation gap.** The derivation follows the highest-wins rule exactly: active computer task (running|paused) OR computer-class confirm pending → L2; browser confirm OR recent browser tool within quiescence → L1; else → L0. Pin uses `max(pin, derived)` which blocks auto-down only — matching D13. D15 hysteresis works via `computerTaskStatus === "finished"` + `finishedAt` within window. However, there is **no explicit `"aborted"` status** in `ComputerTaskStatusInput` — the `reduceComputerTaskEvent` reducer maps task termination to `"finished"` regardless of ok/fail/aborted, so the quiescence window is preserved. This is correct behavior but depends on the reducer always populating `finishedAt` for every terminal state. **Recommendation:** add a comment in `deriveCapabilityLevel` noting that `"finished"` includes aborted/cancelled paths.

D9′ (no auto-promote L1 by step count) is respected — ModeController only changes level; Cockpit auto-open only triggers for L2.

D10′–D12′ are addressed in P1 code (see below).

D14 (confirm timeout) is partially implemented (see Q3).

D16 (tray-initiated L2 opens Cockpit) is handled by background's `handleCompanionMessage` triggering `openOrFocusCockpit` on `computer.task.event` started/paused.

### Q2 — Is dual-surface state (separate stores) acceptable for P1, or is it a ship blocker?

**Acceptable for P1.** Both surfaces receive the same WS broadcast via `chrome.runtime.sendMessage`. The companion is the authoritative source; both stores re-derive independently. The architecture is honest about its limits: races on concurrent mutations from two surfaces (e.g., user sends follow-up from Panel while conductor sends from Cockpit) are possible but the companion processes messages sequentially per thread, so the worst case is two messages in quick succession — which is already possible with rapid user typing. No shared-memory corruption is possible because there is no shared memory.

The real risk is **SW death resetting `cockpitWindowId`** (module-level variable lost), causing a duplicate Cockpit on next `openOrFocusCockpit`. This is a lifecycle gap (see Q6) but not a ship blocker for P1.

### Q3 — Safety: can the user always abort and always see a confirm path if Cockpit is closed/unfocused?

**Abort: yes.** The SafetyStrip's "急停" button is always rendered when `task && !finished && !task.abortAcked`. If the user closes Cockpit, the Panel SafetyStrip remains visible, and abort is a single click away. The 3s unconfirmed abort warning with `Ctrl+Alt+End` fallback message provides an escape hatch.

**Confirm path: yes, always visible in Panel.** `MinimalConfirm` renders whenever `pendingSecurityConfirmations.length > 0` during L2, with Allow/Deny/Deny+Stop + "详情↗" to reopen Cockpit. If Cockpit is unfocused and a new confirm arrives, the background auto-focuses it AND the Panel shows `MinimalConfirm`.

**But there is a timeout gap:** when in L1 mode (not L2), the full `SecurityConfirmationDialog` has no timeout. Both Cockpit `ConfirmElevated` (60s) and the spec D14 require timeout. A stale L1 confirm could sit indefinitely. This must be fixed.

### Q4 — Content-split confirm: does MinimalConfirm + ConfirmElevated satisfy security without regressing whitelist/nonce paths?

**Yes, with one regression in Cockpit nonce anti-paste.** The split itself is correct:
- **Panel `MinimalConfirm`**: tool name + risk + Allow/Deny/Stop only. Sends `add_to_whitelist: []` — no whitelist escape. Safe.
- **Cockpit `ConfirmElevated`**: full preview, whitelist radios, nonce challenge.

**The regression:** Cockpit `ConfirmElevated` nonce input only blocks `onPaste={(e) => e.preventDefault()}`. It does NOT block:
- Ctrl+V / Cmd+V keyboard shortcuts
- Shift+Insert
- Right-click → Paste (context menu)
- Drag-and-drop text

The Panel `SecurityConfirmationDialog` has comprehensive blocking: `onKeyDown` (blocks meta/ctrl+v, shift+insert), `onContextMenu`, `onDrop`, and `onPaste`. This is a **real security gap** for nonce-protected confirms in Cockpit. Severity: medium (requires physical keyboard access to Cockpit window; nonce is visible on screen in the same window).

Thread-trust/session-trust checkboxes are missing from Cockpit `ConfirmElevated` but present in Panel dialog. Since the Panel dialog is hidden during L2, these trust mechanisms are effectively disabled for L2 operations. This is acceptable for P1 (trust is a convenience, not a security boundary) but should be added in P2.

### Q5 — Input ownership D12′: is current Panel behavior honest enough, or must send be gated?

**Honest enough for P1.** The InputArea in L2 mode shows: placeholder `"排队跟进…（主指令请在操控台发送）"`. The send button still fires `chat.send` normally — there is no gate. The user CAN send task instructions from Panel during L2.

This is the design the self-report acknowledges ("visual '排队跟进' only; not a true queue"). Given that:
- Cockpit is prominently opened on L2 entry
- Both surfaces send through the same companion, which processes sequentially
- The composer grey-states with the hint text

…the implementation is honest: it signals intent without blocking. Hard-gating Panel `.send` during L2 would be safer but risks frustrating users who genuinely need to send a quick follow-up without switching windows. P2 should consider a "confirm intent to send from Panel during L2" interstitial rather than a hard block.

### Q6 — Window lifecycle: open/focus/close/onRemoved — races, multi-window, SW death?

**Functional but fragile.** The singleton `cockpitWindowId` pattern has two failure modes:

1. **Concurrent `openOrFocusCockpit` race:** If two companion events trigger `openOrFocusCockpit` in rapid succession (e.g., `security.confirmation.request` + `computer.task.event` in the same message batch), both calls see `cockpitWindowId === null`, the async `windowExists` check may pass for both (no window yet created), and both calls to `chrome.windows.create` proceed — producing **two Cockpit windows**. No mutex/lock exists.

2. **SW death:** `cockpitWindowId` is a module variable lost on service worker restart. On next `openOrFocusCockpit`, a new window is created even if the previous Cockpit window still exists (user may be looking at it). The old window becomes zombie — it receives broadcasts but has no `cockpitWindowId` tracking.

`onRemoved` is correctly wired via `ensureOnRemoved()` (idempotent hook). `closeCockpit` sets `cockpitWindowId = null` before `chrome.windows.remove` to prevent races with `onRemoved`.

These are acceptable for P1 with a documented limitation. P2 should add a promise-based mutex and SW-restart recovery (query existing windows for Cockpit URL).

### Q7 — What must be fixed before human product confirmation / merge?

1. **Cockpit nonce anti-paste hardening** — add `onKeyDown` (block Ctrl+V, Cmd+V, Shift+Insert), `onContextMenu` (prevent default), and `onDrop` handlers to Cockpit `ConfirmElevated` nonce input, matching Panel `SecurityConfirmationDialog` protections.

2. **Panel SecurityConfirmationDialog timeout** — add 60s auto-deny timer to the full confirm dialog for L0/L1, matching spec D14. The timeout should auto-deny and dispatch `REMOVE_SECURITY_CONFIRMATION`.

3. **Cockpit window creation lock** — wrap `openOrFocusCockpit` with a promise-based mutex to prevent concurrent `chrome.windows.create` calls producing duplicate windows.

4. **Document the SW-death duplicate-window behavior** in a known-limitations section of DESIGN.md or the Cockpit module comment.

## Must-fix before human confirmation

1. **Nonce anti-paste in Cockpit `ConfirmElevated`** — missing keyboard shortcut blocking (Ctrl+V, Cmd+V, Shift+Insert), context menu blocking, and drop blocking. The Panel `SecurityConfirmationDialog` has comprehensive protections; the Cockpit has only `onPaste`. Severity: medium. Fix: copy the four-handler pattern from `SecurityConfirmationDialog` nonce input.

2. **Panel `SecurityConfirmationDialog` lacks timeout** — no auto-deny timer. Spec D14 requires timeout for confirms; Cockpit has 60s timeout but Panel full dialog does not. A stale L1 confirm could sit indefinitely. Severity: medium. Fix: add `useEffect` with 60s `setTimeout` calling `decide(false)`.

3. **`openOrFocusCockpit` race condition** — concurrent calls can create duplicate Cockpit windows. No mutex/lock. Severity: medium. Fix: add a module-level `let cockpitOpenPromise: Promise<number | null> | null = null` and chain concurrent calls onto it.

4. **SW-death duplicate window documentation** — `cockpitWindowId` is lost on service worker restart. When acknowledged but not yet fixed, this must be documented in the Cockpit module header comment. Severity: low (documentation).
