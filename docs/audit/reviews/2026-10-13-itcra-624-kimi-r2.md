  **Adversary r1 blocker — production shutdown never closed the enterprise singleton (REJECT driver). Fixed.**
  `enterprise-http.ts` adds `closeEnterpriseHttp()`: it sets a permanent `shuttingDown` fence and closes an already-created singleton only — it never instantiates the lazy service just to stop it. Both `service()` and `handleEnterpriseHttp` deny `SERVICE_SHUTTING_DOWN` (503) before any instantiation path, so teardown cannot race a lazy reopen. `ws/lifecycle.ts` calls it as the first statement of `shutdown()`, before any awaited ACP/MCP/history/HTTP teardown, wrapped in try/catch. The new loopback test exercises the real lazy path: closing an empty singleton creates no lock; a live request creates the lock; shutdown removes it; three late requests all get 503 `SERVICE_SHUTTING_DOWN` with no lock recreation; admission recovers only after the test reset. I checked the interleaving explicitly: `service()` is synchronous from the flag check through constructor and lock acquisition, so there is no window where a singleton is constructed after the fence is set — if `service()` starts first it completes and is then closed; if the fence is set first, `service()` denies.

  **Kimi r1 P1 — A-B-A unlink race in lock release. Fixed.**
  `lockEnterpriseState` now records `fstatSync(fd)` at acquisition and, on release, `lstatSync`s the path and unlinks only when dev+ino match and the entry is still a file. Because the descriptor stays open until after the comparison, the owner's inode cannot be freed and reused during the check — the guard is sound, not probabilistic. The new fault-injection test covers exactly the r1 scenario: operator removes the "stale" lock while the old writer is still alive, a successor acquires, and the old writer's `close()` must not remove the successor's lock (verified: `STATE_BUSY` on a third attempt).
