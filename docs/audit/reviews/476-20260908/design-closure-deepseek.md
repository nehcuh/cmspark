**FINDINGS**

**Identity — underspecified at the trust root.** Slice 2 promises "a separate typed local desktop identity" with allowlisted methods and payload checks, and Slice 4 demands "explicit origin ownership" with challenge/action binding. But the plan never proposes *how* the desktop host acquires or proves that identity. What is the trust anchor — a per-installation keypair exchanged through a pairing ceremony, an OS-verifiable local socket with PID/PATH attestation, a signed token from the Companion backend? Challenge binding, source-bound event delivery, and "never accept an extension confirmation ID in the desktop channel" all presuppose this root; without it, a desktop client that can assert any identity defeats every downstream check. This must be specified before Slice 2 is accepted, not discovered during implementation. Related: no revocation/rotation story for desktop credentials, and the legacy tray-client audit ("no silent global ACL removal") is scheduled *inside* Slice 2 rather than as a blocking precondition with explicit pass criteria and regression acceptance proving omitted clients keep their current behavior. Move it out front; if the audit changes the design, Slice 2's shape changes.

**Confirmation sequencing — the slice order contradicts the mandated order.** The corrections section states a binding order: "desktop identity + confirmation → … → new terminal/agent execution → browser task policy → native/package." The slice list violates it: Slice 3 (Local work: PTY/ACP execution, "local explicit terminal gestures") lands before Slice 4 (Desktop confirmation). The plan itself concedes confirmation "is a dependency for sensitive standalone tools, not a late cosmetic step" — but terminal/agent execution in Slice 3 *is* the sensitive standalone tool. As written, either Slice 3 ships execution before the confirmation channel exists (violating the mandated order), or Slice 3 is secretly read-only and its acceptance text is misleading. Fix by renumbering: confirmation must precede or gate any slice that spawns new execution. Also verify Slice 2's "local explicit terminal gestures" don't implicitly require the confirmation channel before it exists. The reuse of the existing security confirmation manager with connection+thread+action/challenge+expiry binding and cancel-on-disconnect is otherwise correct; add one explicit test that a desktop channel cannot redeem a challenge issued to another surface even with a valid ID.

**Acceptance gaps.** (1) No acceptance criterion anywhere for the "quiet" outcome or the summon action: global hotkey registration, OS accessibility/input-monitoring permissions, avoid-stealing-focus behavior, conflicts with the pack's icon/history work (#475). The only mention is a keep-the-icon note. Native packaging (Slice 6) should own this. (2) The concrete test list (missing peer, denied mutation, stale async list response, stop with navigation open, reconnect, cross-thread outputs) is not mapped to owning slices; "denied mutation" is meaningless without stating *which* mutation on *which* surface. Enumerate exit criteria per slice, not as a shared pool. (3) "Machine checks before implementation release review" is undefined — state what the machine validates (render at the four widths already listed, plus which slice's assertions). (4) No acceptance for default window geometry (1040x760 / 360x420) or for workspace-open-while-quick-mode-alive lifecycle. (5) Browser slice says "background means avoid foreground activation where supported" — specify what "supported" is measured against (adapter capability matrix? Chrome version?) and require the unsupported case to be a tested path, since silent foreground fallback is already cited as an existing flaw in client.ts.

**Positives.** Honest gap accounting (Chromium shell vs. native hosting is correctly pinned to #477 with #476 not closeable), correct constraints on MCP mutation denial and no second confirmation queue, good information architecture, sensible no-Codex scoping.

**VERDICT: REJECT**

The confirmation ordering contradiction plus an unspecified identity trust anchor make this unshippable as a privileged-desktop design. Fixes are well-scoped: define the identity root and provisioning/revocation, renumber slices so confirmation precedes execution (or explicitly degrade Slice 3 to non-sensitive output only), add per-slice exit criteria, and add summon/hotkey/quiet acceptance under Slice 6. Resubmit after edits; this should not require wholesale redesign.
