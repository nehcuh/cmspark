## 2. S6 — revocation/policy rollback: independently confirmed repaired

Root cause (r3): `verifyOutboundGrantToken` re-saved the whole authority file from a stale in-memory snapshot to touch `last_used_at`, so a concurrent revoke/policy write could be silently rolled back, and a later "live" reload accepted the rolled-back store.

Repair verified in source:
- Authentication no longer writes authority JSON. The only write is the per-grant sidecar at `companion/src/outbound-mcp/outbound-grants.ts:336-341` (`usagePath(rec.id)` → `atomicWriteJSON(usage, {last_used_at}, 0o600)`), and listing overlays it (`outbound-grants.ts:150-158`, `listOutboundGrants`). A usage race is last-writer telemetry and cannot restore `revoked_at` or an older revision.
- Authority writers serialize: `mutateGrants` (`outbound-grants.ts:142-149`) takes an exclusive `wx` lock **before** a fresh `loadFile()`, held through the `atomicWriteJSON` rename; contention → `GRANT_STORE_BUSY`, non-EEXIST → `GRANT_STORE_UNAVAILABLE`, lock released/unlinked in `finally`; no age-based stealing. All three supported writers use it: issue `:232`, revoke `:360-372`, revoke-all `:376-386`. Root grep confirms only these three `saveFile` calls exist in `companion/src`.
- Live use is file-based, not cached: `requireEnterpriseGrant` (`:403-411`) re-loads and re-validates revoked/expiry/instance/subject/policy≤grant, and every enterprise request/`bound()` re-runs it (`enterprise-service.ts:83-99`). So even a hypothetical residual stale write is rejected at use.

On the specific question the task poses: **a live reload alone would not have been sufficient** — after a successful rollback the file itself is "valid," so re-reading it accepts the rolled-back state. The closure is genuinely the two-part fix (no authority write on auth + full writer lock), and the card does not rely on reload-driven monotonicity. The child-process regressions (`outbound-grant-concurrency.test.ts`) pause after a real authority read and interleave real revoke/revoke-all/policy writes from a separate process; they select an interleaving but do not replace production verification/mutation logic, which is the correct way to test this. I do not find an overclaim here that needs correction.

Boundary I note but cannot close from source alone: `/tmp` corpus excluded and my lane cannot prove no writer outside `companion/src`; the supplied grep plus full `outbound-grants.ts`/`io.ts` bodies show no other authority writer inside the shown scope. `io.ts` `atomicWriteJSON` is atomic-rename only, which is exactly why the lock — not the helper — is load-bearing.

Root cause (r3): with overlapping navigation/login scopes, the tab-history observer excluded login-scope URLs and could keep the older ready URL A after an A→B→same-route-login transition, so the service prepared/restored/read A.

Repair verified:

- The producer→JSON→service regression reproduces the original failure shape (explicit failure, zero restore, no A text, no private URL in state) and the recovery shape (B once, one restore, no click replay). Contract/ADR declare the remaining unknown cross-route overlap as an explicit support limit rather than guessing — consistent with the handoff's "declare unsupported, never convert failure into evidence."

Nuance, not a security defect: a genuinely ready B followed by a redirect to a *different* login route that lies in both scopes clears the destination and fails closed. That matches the contract's "same-origin overlap limit" clause; it does mean the phrase "previously ready B continue normally" only holds for same-URL modal login. I flag it as a documentation-precision nit (§5), not a boundary breach.

## 5. Disposition of Kimi nits (independent assessment, not blind adoption) and residual findings

**N1 — nonbranded return-false branch (`server.ts:475`).** I do not accept "dead code" as stated: for a *typed* `EnterprisePermit` it is unreachable, but at runtime `invokeOpts` is untyped, so a non-branded lookalike takes the `false` branch and returns `PERMIT_INVALID`, while a branded mismatch throws `EnterpriseError`. The branch is reachable defense-in-depth; the real observation is inconsistent error surfaces (throw vs. result envelope). Fail-closed, no authority impact. **Disposition: P3 nit, non-blocking.** Do not waive.

**N2 — error-code diagnostics (`enterprise-browser.ts:211-212`).** Confirmed: the allowlist omits `TAB_HISTORY_CAPACITY` (`:52`) and `FRAME_UNAVAILABLE` (`:103,107`), and Chrome's "document no longer available", collapsing them to `ENTERPRISE_BROWSER_UNAVAILABLE`. Fail-closed but loses operator specificity. **Disposition: P3 nit, non-blocking.**

**N3 — presentation challenge consumed before failed ready check (`enterprise-service.ts:379-386`).** Confirmed: `validateProof` then `session.presentation = challenge; save()` occurs before `inspect`/`LOGIN_VIEW_UNAVAILABLE`. Only the independently authenticated ITCra signer can trigger it; consequence is a forced QR refresh (self-DoS). Validating state before rotating would be cleaner. **Disposition: P3 nit, non-blocking.**

**N4 — internal frame URLs and encoded-path support.** Frame URLs (including out-of-scope/third-party ticket-like query strings) do enter the in-memory `Snapshot`, the `operation_digest`, and challenges — but only as SHA-256 digests in durable/public surfaces; public session/operation envelopes do not expose frames, and the `review` object carries only args/digest. So the written "no private URLs" contract holds for durable/public surfaces. Separately, `scoped()`/`canonicalURL` reject **any** `%` in the path (`enterprise-browser.ts:39-46`, `enterprise-policy.ts:55-66`), so legitimate percent-encoded in-scope paths fail closed; that is intentional and documented ("encoded path aliases … rejected"), but the blanket `%` rejection also rejects benign encodings and should be stated as a config requirement (use decoded paths). **Disposition: P3 nit + documentation line, non-blocking.**

**NEW residual P2 — durable-state lifecycle never prunes; caps become permanent.** `EnterpriseBrowserService` keeps every session and operation forever: the restart loader only rewrites states (`enterprise-service.ts:51-66`) and never removes them, and there is no pruning/eviction anywhere (no `splice`/filter/rotate; only `outputs`/args maps are trimmed). `open` hard-rejects at `this.store.sessions.length >= 128` (`:196`) and `prepare` at `operations.length >= 1024` (`:243`). Because terminated sessions and completed operations persist across restart, a long-running deployment reaches the cap and then **permanently** rejects new sessions/operations until an operator deletes/rotates `enterprise-browser-state.json` — which the contract does not describe as a supported procedure and which conflicts with "corrupt/unwritable state fails closed" and the idempotency-retention intent. Real evidence: the code above plus the contract's own cap statement (which does not mention pruning or a rotation procedure). This is availability/operability, not an authority breach, so it does not flip either source verdict, but the contract lane's "no residual P0/P1/P2" is overstated. Recommended repair: prune terminal sessions/completed operations past policy/session expiry under the writer lock, or explicitly document and test an operator state-rotation procedure. **Disposition: P2, non-blocking for source approval; should be fixed or explicitly documented before sustained production.**
