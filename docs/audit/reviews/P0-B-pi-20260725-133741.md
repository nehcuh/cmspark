### Non-blocking nits

1. **`messages.pop()` dead-code fallback** (`adapter.ts:910`): In the `shouldStop` path, `savedAssistantId` is always set (assistant message is persisted at L527 before tool-execution for-loop begins). The `else { messages.pop() }` branch is unreachable defensive code. Harmless but misleading.

2. **`chat.aborted` handler uses `activeThreadRef.current` directly** (`useWebSocket.ts:200-212`): Unlike `chat.done` which prefers `msg.thread_id` via `doneThreadId`, the `chat.aborted` ADD_MESSAGE uses `activeThreadRef.current` directly for `id` and `thread_id`. Since `shouldApplyStreamEvent` already gates, the values are equivalent in practice, but the inconsistency with the `chat.done` pattern is a minor style nit.

3. **Ungated `tool.start`/`tool.result`** (residual, out of scope): As noted in the design doc and adversarial summary, tool events are not gated by `thread_id`. This is explicitly deferred. Not a P0-B regression.

4. **`rebuildMessagesFromHistory` dual `openToolCallIds.clear()`** (L167, L178): The set is cleared in both branches of the `validToolCalls` if/else. Could be hoisted once before the branch.

VERDICT: APPROVE
