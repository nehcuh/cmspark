## Blocking issues

### B1. `LICENSE_DOOR_TEXT` body + footer still promise "永久跳过 + 手改 config.json" — direct user-visible contradiction inside the license modal

`companion/src/computer/model-license.ts:120`:
```
- 拒绝本许可则本实验层永久跳过（复位 = 手改 config.json）。
```

`companion/src/computer/model-license.ts:125` (footer of LICENSE_DOOR_TEXT):
```
拒绝则本实验层永久跳过，其余定位层不受影响。
```

This text is the `licenseText` field of `computer.model.license_required` (`companion/src/computer/model-handlers.ts:340-345`) and is rendered as the modal body at `chrome-extension/src/sidepanel/components/SettingsSlideout.tsx:1046`. Immediately below it, the same modal renders the `notice` field (`SettingsSlideout.tsx:1049`) which r3 updated to:

> "阅读并接受许可证与免责声明后可开启实验层；拒绝则本层跳过，其余定位层不受影响。**之后可在设置页「复位许可拒绝」重新打开流程。**"

So inside one modal the user reads:
- license body: "拒绝本许可则本实验层**永久跳过**（复位 = **手改 config.json**）"
- notice below: "拒绝则本层跳过…之后可在**设置页「复位许可拒绝」**重新打开流程"

Then if the user clicks 「拒绝(跳过本层)」 they see the post-decline `licenseDeclinedNotice` (`model-state-messages.ts:250-253` / ext mirror `model-switch-logic.ts:229-231`): "可在设置页「实验层」重新打开许可流程以复位拒绝（**无需手改 config.json**）".

Three surfaces in the same flow, two of them now contradict the third — and the contradiction is on a security-relevant promise (whether a permission is permanent and whether reset requires editing `~/.cmspark-agent/config.json` by hand). The user cannot form an accurate mental model of the decline's blast radius.

This is the same shape of bug r2 blocker #2 caught ("pre-decline promise vs post-decline reality"); the r3 fix updated `notice` + `licenseDoorHint` + `licenseDeclinedNotice` (4 of 5 user-visible pre-decline surfaces) but missed `LICENSE_DOOR_TEXT` itself — the most prominent surface because it IS the license the user reads. The commit message "Align pre/post decline copy (no false 永久跳过)" is an overclaim.

The fix is straightforward: rewrite lines 120 and 125 of `model-license.ts` to advertise the settings-page reset path (consistent with the notice). `LICENSE_DOOR_TEXT_HASH` at `model-license.ts:135-138` is recomputed at runtime from the text, so previously-accepted users will be re-prompted — this is the **desired** behavior (terms changed → re-accept), and is exactly what the P1 hash-binding mechanism was designed for ("文本漂移 → 哈希不符 → 重新弹门").
