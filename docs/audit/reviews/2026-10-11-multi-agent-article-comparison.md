## 总体判断

CMspark 已经实现实质性的 **Supervisor + Blackboard + 部分确定性状态控制**。它能创建独立 worker 线程、控制权限与并发、等待并收集结果，并在结果层统一浏览器任务与 ACP。尚不能称为完整通用 Graph/StateFlow 执行器、自动流水线、默认 Debate 共识系统或自主 Swarm，也没有实现第二篇的 PANDA 分布式架构。第二篇使“中断后保留进度并继续执行”的缺口更明确；不改变小规模本机协作应保留明确权限与控制责任的判断。

多种模式并不是必须全部实现的清单。当前集中控制权、禁止 worker 递归派发与互聊，是有明确边界的产品选择。优先补齐任务验收和恢复可靠性，比为了凑齐六类模式增加自由互聊更有价值。

## 六类形式的实现程度

| 文章模式 | 当前实现 | 判定与边界 |
|---|---|---|
| Supervisor / Coordinator | 父线程派发 worker，专家包提供角色与工具面；普通结束前运行时监督等待、收集、显示异常，再继续综合 | 核心形式已实现。任务拆解、质量验收与是否补做仍主要由模型判断；没有通用自动纠错调度器 |
| Graph / StateFlow | `loop_state` 控制预算与停机；统一任务状态持久化；Intent 依赖检查拒绝缺失、循环和未完成依赖 | 部分实现。依赖检查是认领门禁，没有任意 DAG 的 ready 队列、自动调度、节点重放与跨重启执行恢复；`workflows/*.ts` 仍是历史 playbook |
| Sequential Pipeline | 技能步骤、明确代码流程；统一 `task_result`、有限摘要与原文片段接口 | 有构件，未实现通用流水线。没有统一的阶段输入输出验收、自动串接与失败回滚 |
| Blackboard / Shared State | MissionBoard 的 Fact / Intent / Hint、来源信任、认领、心跳、线程锁；父线程收集后写入共享状态 | 实现受控黑板。默认 worker 不直接自由读写 Board，也不监听环境变化自主触发；散文报告可收集但不写成结构化事实 |
| Debate / Consensus | 专家角色包能够分视角工作；仓库开发过程有独立 finder 与 skeptic 复审 | 产品未默认实现多轮交叉质询、裁判或投票共识。开发评审流程不能当作产品能力；不同角色也不保证不同模型 |
| Dynamic Handoff / Swarm | ACP 将编程任务交给外部执行器，结果和状态读取共用协议 | 存在任务委托与接力，但父线程仍拥有用户对话；没有 worker 间自主控制权转移或统一执行调度 |

## 文章中的问题是否存在

| 问题 | 当前缓解 | 仍存在的风险或不适用之处 |
|---|---|---|
| 中心性能与上下文瓶颈 | 父线程等待时释放并发槽；模型结果投影默认只给 1200 字符摘录、来源及有限事实，原文分页可读 | 主线程仍独占拆解和综合。进程多智能体模型槽共 5 个，父线程也计入；提高 worker 数不会自动提高吞吐。1200 字符是前缀摘录，关键结论在尾部时需主动读取 |
| 图约束与模型规划冲突 | 依赖校验、权限门禁、停止状态和预算由代码控制；先评估任务是否适合并行 | 模型提出目标不等于图已完整。检查依赖没有生成、调度和自动修复依赖链；建议器对任务能力的判断仍可能有误 |
| 上游幻觉或误差向下游传播 | 工具报告包裹为不可信数据，Fact 信任重打标；异常、局部报告与运行完成分开 | `completed` 表示运行结束并有报告，不表示答案正确或目标覆盖充分。`tool_verified` 核验了可解析的工具调用来源，并不证明该来源支持每一句主张。`board_complete` 要至少一项较高信任事实，也不等于逐个验收成功条件 |
| 黑板读写冲突与一致性 | Board 变更经过线程锁和原子保存；认领/心跳以及结果版本、归属检查减少重复或过期合并 | 单进程控制优于任意自由共享，但不是分布式一致性方案。任务元数据持久化不等于执行进程、队列与所有中间步骤能够恢复；ACP 原文只保证会话生命周期可读 |
| 辩论震荡、难收敛 | 默认产品没有自动多轮辩论，存在轮数和任务预算 | 不是已观察到的产品辩论死循环。将来引入评审应有分歧触发、固定轮数和证据裁决；多角色一致本身不能证明正确 |
| 长移交链循环 | worker 禁止嵌套 spawn、互聊和 ACP；spawn 需确认 | 当前不开放任意自主移交链，显著限制了该类循环。浏览器和 ACP 虽共用结果协议，等待/取消/重启与权限仍是不同路径 |

当前限制：同 run 占用 worker 名额最多 5，终局释放；累计创建预算 20（回收站不退款，硬删/创建回滚的口径另行定义）；专家队伍最多 4；普通监督等待期限 10 分钟。有限恢复预算目前是恢复建议，不是自动副作用重试器。

## 已经补齐的内容

旧的 2026-10-07 评估曾列出“统一结果协议”“任务状态与依赖”的缺口。最新代码已部分补齐，不能继续把它们全部列为未实现：

- 浏览器和 ACP 的 `task_result` 共用状态、有限摘要、来源版本、缺口与恢复建议。
- 父线程保存最多 64 项有界协作状态，同版本幂等、旧归属失效检查与有限失败版本计数。
- Intent 依赖校验及认领门禁已存在。
- 原文可按 `report_offset` / `report_limit` 显式读取；分页仍应核对版本，不能将不同版本拼接成一份报告。
- 普通结束前有真实收集兜底；暂停、用户停止和安全阻断不会被自动重启。

## 建议优先级

1. **优先完善业务验收与证据支持关系。** 将“运行完成”“有报告”“满足任务成功条件”分开；对结论覆盖、证据支持和相互矛盾做验收，只补做缺失部分。现在的来源校验应保留，但不把它升级解释为事实真实性验证。
2. **围绕有依赖和可恢复任务补调度能力。** 依赖就绪、blocked 原因、检查点与执行状态应连起来。对读操作、幂等操作和有副作用操作分别决定是否可以重试；保留人工停止和安全终止的恢复边界。无需首先迁移整个框架。
3. **测量协作是否值得。** 用同一组真实任务对比单 agent、2 worker、4 worker，评估目标覆盖、事实正确率、延迟、token、重复劳动与失败恢复率。目前的 16 案例 Fleet 评估测的是“是否建议并行”，不能证明实际协作更快或更准确。
4. **继续统一协作生命周期与能力描述。** 共用结果协议之上再考虑一致的等待、取消、失效、原文可用性及状态解释；每种执行器保持自己的权限边界。辩论只针对高分歧环节；自由互聊与自主移交暂时没有足够收益证据。

概念校验：[OpenAI Agents SDK 编排文档](https://openai.github.io/openai-agents-python/multi_agent/)明确区分 manager 保留控制权与 handoff 让专家成为活动 agent，也允许模型规划与代码控制混合；[LangGraph 持久化文档](https://docs.langchain.com/oss/python/langgraph/persistence)区分图状态检查点与跨线程持久存储。本文据此区分委托、控制权移交、保存记录与执行恢复，不声称 CMspark 拥有这些框架的全部能力。

## 第二篇补充：PANDA 与当前项目

第二篇强调分布式通信、拓扑与编排分离、故障替换和 WoT。论文的核心场景是由不同管理者运营的 Agent 集合；CMspark 当前是单机 Companion 管理的小型任务队伍。下面是实现对照，不是对两者做过同条件性能测试。

| PANDA 机制 | CMspark 当前实现 | 判断 |
|---|---|---|
| 集合通信与任务队伍通信分开、能力发现 | 本机 WS 工具总线、已安装 Pack 和角色候选匹配；没有分布式 Agent 能力注册表、集合 gossip 或跨节点组队协议 | 不具备分布式发现与通信；当前小队规模下不能据此认定已有通信吞吐缺陷 |
| 可选 star / chain / mesh 编排 | 父子线程主要构成 star；依赖门禁和结果投影提供部分基础；worker 不互聊、不嵌套派发 | 不支持通用拓扑切换。共享 FIFO 并发槽不等于 Agent 跨团队接单和节点级负载均衡 |
| 故障检测、保留执行进度、替换故障执行器 | 监督识别超时、异常、空报告与局部报告，提供有预算的恢复建议；有状态元数据和版本守卫 | 可检测和披露，但没有自动保留所有阶段状态后替换节点继续跑；`automatic:false` 是明确恢复边界 |
| 不同管理域 Agent 的 WoT 认证 | 本机配对、权限闸、HARD_DENY、Pack 信任与 Fact 来源信任 | 已有治理，但不是 WoT。Fact trust 是证据来源等级，不能当成 Agent 身份认证网络 |

对应代码锚点：`orchestrator/constants.ts:3`、`expert-team.ts:145`、`llm-loop-gate.ts:21`、`fleet-supervision.ts:44`、`cooperation-result.ts:29`、`threads/thread-manager.ts:548`、`acp/session-recovery.ts:13`（均在 `companion/src/` 下）。

### 帖子转述需要保留的实验边界

- **没有全局中心不等于取消所有主从。** PANDA 明确保留任务内的 star 编排；因此不应从帖子推导“主线程存在即落后”。论文同时讨论协调者故障监控与检查点。
- **组队规模不等于同规模推理实测。** 大集合测试测的是团队组建；问答实验配置为 10 worker、200 个 HotPotQA 任务、并发 5。不能把百万规模组队解释为百万 Agent 同时进行端到端问答。
- **8 倍不是所有任务的统一加速。** 表 2 的性能依基线、知识配置和拓扑而变，也有准确率取舍，不能推导 CMspark 更换架构后会得到相同倍数。
- **100% completion 不是 100% 正确。** §3 定义 completion 为产出任意答案，无论正确与否。崩溃注入实验的具体完成率不是任意浏览器写操作都可无损恢复的保证。

以上依据为 [PANDA §2.4–3.2](https://arxiv.org/html/2609.38482v1)。帖子中“通信中断”的宽泛表述，不能扩展成已验证任意网络分区、全部节点失效或业务副作用故障模型。

### 我们是否有第二篇指出的问题

**共享故障域存在。** 原生 worker 共用 Companion 进程；进程退出时，内存中的 deferred kick 队列、live 工具结果镜像与 ACP 会话句柄不能凭保存的状态元数据继续执行。`threads/thread-manager.ts:548–553` 明确说明 live mirror 不落盘，重启回退到归档摘要；`acp/session-recovery.ts` 也明确旧会话需要重新提议和确认。没有协调者接管和跨进程检查点恢复。这是源码可确认的能力边界，本次没有对正在工作的应用注入崩溃。

**单个 worker 异常并非必然拖垮全队。** 最新监督能收集其他任务结果、披露缺失，并在等待超时后给出恢复选择；第二篇对中心化系统的概括不能直接套成我们的必现 bug。真正尚缺的是故障后接续、按能力替换执行器和固定已验收成果，而非仅仅有没有错误提示。

**中心吞吐限制存在，但不是当前已经实测的规模瓶颈。** 我们明确限制并发和 worker 数，主要解决本机浏览器小队任务。没有千节点负载测量，不能直接声称已发生帖子描述的规模性拥塞，也没有证据应立即付出 P2P 与 WoT 的维护成本。

### 据第二篇调整改进顺序

1. **先将已验收进度变成可恢复检查点。** 保存阶段输入引用、产物引用、依赖、执行版本和故障原因，明确重启后哪些可复用、哪些待确认；不要为恢复无条件落盘全部敏感工具正文。
2. **再做受控故障替换。** 对可恢复故障，仅重派未完成子任务；保留已验收结果。版本守卫应覆盖执行尝试，防止迟到结果覆盖新结果，以及同一写操作被旧、新执行器重复执行。暂停、用户停止和安全阻断保留现有恢复边界。
3. **用匹配能力与当前负载改进小队调度。** 先针对本机队列等待、独立任务和来源选择测收益；跨机器、跨组织的需求得到验证后，再评估 gossip、网络 Agent 身份与 WoT。
4. **补故障实验，而非只数完成任务。** 测试 worker 超时/崩溃、父线程中断、Companion 重启、迟到结果和部分成果复用，分别统计正确率、目标覆盖、恢复率、重复副作用、耗时和成本。此前 160 项测试通过不等于这些完整故障场景已验收。

上述是评估建议，没有修改产品源码、权限或运行配置，也没有新建需求 spec/plan。
