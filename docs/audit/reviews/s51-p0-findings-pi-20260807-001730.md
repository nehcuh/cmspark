# Pi re-review S51 findings

## C1 Trust trash cookie — **CONFIRM** (HIGH)

**Evidence (live tip, empirically verified):**
- `pack-engine.ts:391-408` `releaseTrustBeforeThreadGone` → `restoreTrustFromThreadCookie` → `restoreTrustSnapshot` writes the stored snapshot into live config. Docstring at `pack-engine.ts:235-236` admits it "does not clear the cookie".
- `message-router.ts:1192-1193` (`thread.delete`) and `message-router.ts:1346-1349` (`thread.batch_delete`) call `releaseTrustBeforeThreadGone` for **both** trash and hard modes.
- `thread-manager.ts:378-386` `trash()` only sets `trashed_at` — cookie stays on the trashed thread; `get()` (thread-manager.ts:503) returns trashed threads.
- UI hard-delete from trash: `ThreadList.tsx:292` sends `batch_delete mode:"hard"` → release re-fires with the stale cookie.

**Empirical run** (`captureTrustSnapshot`/`restoreTrustSnapshot` against real config):
- Baseline **OFF** (default): apply(ON) → trash(→OFF) → user deliberately sets ON in Settings → hard-delete → **silently reset to OFF** (delete action revokes user's explicit choice).
- Baseline **ON** (user had cruise enabled before apply): apply(ON) → trash(→ON) → user turns OFF in Settings → hard-delete → **cruise silently re-enabled** — exactly the claimed path.

**User impact:** a permanent-delete from the recycle bin is a pure cleanup action, yet it re-mutates live security config from a stale snapshot, in both directions (silent privilege re-grant when baseline was elevated; silent revocation otherwise). This is precisely the "sticky cruise" class the S46 fix was meant to eliminate — the fix is incomplete because the cookie is never cleared at release. Also inconsistent: `purgeExpiredTrash` (`thread-manager.ts:403-420`) hard-deletes with **no** release, so manual delete and 30-day purge diverge. No test covers the trash→settings-change→hard-delete sequence (`packs-engine.test.ts:441` only tests single delete).

**Fix:** clear `mission_pack_trust_snapshot` at release time (make `releaseTrustBeforeThreadGone` idempotent), or clear the cookie in `trash()` so the later hard-delete cannot re-fire; align `purgeExpiredTrash`.

## C2 mid_loop M2 request — **CONFIRM** (HIGH)

**Evidence (live tip, empirically verified):**
- `context-budget.ts:278-280`: the "remove omit notices at end" loop has **no break** — it scans to index 0 and splices **every** existing `[context_omitted]`/`[context_summary]` notice anywhere in the array.
- `context-budget.ts:286-289`: a new notice is inserted with `buildOmitNotice(dropped)` — in M1 (no `rollingSummary`) this is plain `[context_omitted]`.
- `context-budget-m2.ts:88`: `shouldRunM2` returns false for `mid_loop` → adapter.ts:533 skips M2 in the mid-loop pass.
- `adapter.ts:557-573`: the meta keep path preserves `prevMeta.rolling_summary` for「查看摘要」UI but **never re-attaches it into `messages`**; the later `rollingSummary = keepSummary` only feeds the UI notification (`adapter.ts:614`).

**Empirical run** (two-pass through real `compactMessagesTurnSafe`): pre_loop M2 attach → `[context_summary]` present at idx 1. Add tool rounds → mid_loop M1 compaction → `[context_summary]` **gone (idx -1)**, plain `[context_omitted]` at idx 1, summary text absent from request.

**User impact:** on any long task that re-exceeds the window mid-tool-loop, the very next LLM call loses the rolling summary of the earlier conversation — the agent forgets prior decisions/open tabs mid-task. The "Pi nit" comment shows the intent (keep M2 across mid_loop) was only half-implemented (meta kept, request not). No test covers the two-pass pre_loop→mid_loop scenario (`context-budget.test.ts` only tests single passes).

**Fix:** in mid_loop, pass `prevMeta?.rolling_summary` as `opts.rollingSummary` into `applyContextBudget` (or re-attach the meta summary to `messages` after compaction, e.g. via `attachRollingSummaryToMessages`).
