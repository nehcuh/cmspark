## Official API evidence and what remains unknown

[Window.Activate (.NET Framework4.8.1)](https://learn.microsoft.com/en-us/dotnet/api/system.windows.window.activate?view=netframework-4.8.1) documents success/failure and the same activation rules as Win32 SetForegroundWindow. [SetForegroundWindow](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setforegroundwindow) restricts foreground activation; launch by the foreground process is one eligibility condition, and satisfying listed conditions still need not produce success. Thus current evidence supports a denied/unsuccessful request, not the precise policy or a specific competing process. [AllowSetForegroundWindow](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-allowsetforegroundwindow) requires the caller already to be eligible. Blindly granting from the current Node controller would not establish that prerequisite and is not a sufficient repair.

Unknown: actual foreground process at launch/request/check, whether the child ever held foreground earlier, and why this request returned false. No inference from previous green runs or unrelated SDK timing resolves these.

## Smallest useful candidate: one owned OS click during fixture setup

APPROVE as a finite test-setup design for the next independently reviewed implementation and actual Windows run, not as proof of the historical physical cause. It models the existing user-selects-window prerequisite more directly than adding a foreground-right broker, changing WPF event timing, or repeating activation attempts. A direct WPF Focus/UIA/PostMessage surrogate would not prove actual OS selection and adds no established advantage to the current call.

Required boundaries:

1. Only the unshipped scope fixture/controller setup may send input, while its existing surface lease is held. Product activity scripts, recorder, preview, authorization, consent, and model routes remain unchanged. Input is not human approval or a consent event.
2. Derive one interior point from the actual rendered inert read-only TextBox, on its UI thread, for the Current window and the current layout. Reject missing render, stale Current/ReceiptWindow, nonpositive/out-of-client geometry, nonvisible/minimized window, or a point outside that TextBox. No title search, arbitrary supplied target, approval UI, or coordinate fallback. The TextBox has no command/click action in this fixture.
3. Immediately before the only send, require WindowFromPoint(point) and GetAncestor(...,GA_ROOT) to resolve to precisely that Current HWND, with GetWindowThreadProcessId resolving to the owned fixture's actual PID. Check actual hit-test/layout rather than accepting same-process membership alone: WPF content normally shares the top-level HWND. A covering foreign window means refusal with zero input; do not expose, raise, move, minimize, or hide another window to make the test pass.
4. Replace the original Activate/Focus setup pair with one SetupOwnedClick call in the existing requested block, for both the main and independent windows. This is the complete newly reviewed candidate, not a click fallback after a failed activation. SendInput has exactly one batch of three MOUSEINPUT records: move with ABSOLUTE|VIRTUALDESK, left down, left up. Derive absolute coordinates from actual virtual-desktop metrics, including its possibly negative origin, with endpoint-aware normalization to 0..65535. No click/Activate/Focus retries, key tricks, AttachThreadInput, topmost toggles, foreground-lock changes, or polling. A SendInput inserted-count mismatch is a fixture failure, never success; no ready may be emitted from that failed setup. A single batch minimizes interruption but is not an HWND-targeted atomic transaction.
5. Preserve the original ten-second receipt deadlines from their original wait starts (no new sequential setup budget), 180-second native test limit, popup/resize checks, receipt guard, passive before/after HWND equality, crop/title/model/business assertions, and child-close/cleanup/lease ordering. The existing ContentRendered callback invokes the one setup operation per new main/independent window; requested is set before the operation so repeated render/events cannot retry it. Resize does not create a new window or click; only its existing layout and receipt checks run. No new Node waiting protocol is needed.
6. Only the existing event-driven check may publish ready after real foreground and keyboard focus qualify. Neither SendInput's return count nor a clicked marker substitutes for readiness. If the one click does not produce qualification, the original case fails; no fallback or skip.

[SendInput](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput) inserts an ordered event batch subject to UIPI; its return reports inserted events, not accepted ownership or readiness. [WindowFromPoint](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-windowfrompoint) identifies the visible/enabled hit window. [GetAncestor](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getancestor) distinguishes GA_ROOT from root-owner traversal; use the actual top-level root. [GetWindowThreadProcessId](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getwindowthreadprocessid) provides actual process identity, failing closed on a zero return. These APIs do not bind the later SendInput atomically to an HWND. The design must describe that limited test-desktop assumption honestly, without claiming protection from all external desktop races.

## Decision-changing acceptance

CPU controls must consume actual new helper/callsite, not a separately invented guard: current/render/layout/PID/root-hwnd mismatch and covering-window cases each produce zero SendInput; valid inert point produces exactly one fixed batch; short insertion count fails; later events never repeat the batch; successful insertion without real foreground or focus never publishes ready; stale-window events cannot click or publish a replacement window. Retain the existing eight readiness controls unchanged in meaning. Verify no product activation/input change and no timing extension in the final diff.

Then run the existing actual Windows native case once on the approved changed source. The discrimination is concrete: rejected hit/identity precondition identifies setup not safely available; accepted insertion without ready retains OS/input/readiness failure; qualified ready followed by all original business assertions passing establishes that explicitly selecting the fixture satisfies this test prerequisite. It does not prove which OS mechanism denied the old Activate. If popup fails after its own one setup operation, inspect that actual first failure rather than adding another click. A pass must include full OCR/crop/model/independent-window/cleanup behavior; a synthetic setup receipt alone cannot turn the test green.

The source/spec restriction against activating applies to product passive capture, not an absolute ban on selecting the owned fixture during setup. The change must nevertheless be recorded transparently as new synthetic setup input, reviewed by B and GLM before implementation/CI. If the agreed test DoD independently prohibits any new setup input, this candidate is unavailable rather than something to hide inside a helper.
