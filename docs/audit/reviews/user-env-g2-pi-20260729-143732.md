### Nits (non-blocking)

1. **`companion/src/message-router.ts:985,1004`** — Error responses for `user_env.set` / `user_env.delete` omit `family: "user_env"`. The extension falls back to matching `error_code` against `USER_ENV_ERROR_CODES`, which works for all current codes, but a `family` field would be more robust against future error codes not added to the set.

2. **`chrome-extension/src/sidepanel/components/UserEnvSection.tsx:132-134`** — `handleAdd` calls `setNewName("")` and `setNewValue("")` immediately after `sendMessage`, before the companion responds. If the server rejects (e.g., RESERVED_KEY / IO_ERROR), the user loses their typed input. The comment on line 133 ("newValue cleared on user_env.updated") is also inaccurate — the clear happens here, not in the effect. Consider deferring clear to the `userEnvStatus === "已保存"` effect (line 92) for the add flow too, or fix the comment to say "cleared immediately."

3. **`chrome-extension/src/sidepanel/components/UserEnvSection.tsx:242`** — The "保存" button for updating is disabled when the user types `***` into the input (line ~239), matching companion's `USER_ENV_MASK` sentinel semantics. But the disabled state gives no inline feedback explaining why. The placeholder says "输入新值以更新（不会显示原值）" — consider adding a tooltip or brief inline note that `***` is the "unchanged" sentinel and will be ignored.

4. **`chrome-extension/src/sidepanel/hooks/useWebSocket.ts:662-664`** — The `user_env.updated` handler dispatches both `SET_USER_ENV` (which clears error) and `SET_USER_ENV_STATUS` (which also clears error). The double-clear is harmless but slightly redundant.
