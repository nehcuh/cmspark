## Nits

1. **companion/src/capability/shell.ts:201-210** — POSIX argv spawn mis-handles `~/path` args (`cat ~/notes.txt` → literal `~/notes.txt` → ENOENT), `FOO=bar cmd` env-prefix (ENOENT on `FOO=bar`), and `$?`/`$$` refs (literal). Doc comment at :168 ("true PE binaries / #! scripts work with shell:false") still overclaims. Suggest rejecting `~`-word-starts and `=`-prefixed first tokens, and noting argv mode in the shell_exec tool description.
2. **companion/src/skills/skill-install.ts:152-155** — only the *compressed* zip size is capped (25MB); extraction has no decompressed-size/file-count budget (assertDirBudget applies only to the path-dir branch). A 25MB zip bomb can expand unbounded into the user skills root — contradicts the declared "zip/dir size caps" Trust mitigation. Apply assertDirBudget post-extraction.
3. **companion/src/skills/skill-install.ts:48-70** — `isSkillInstallSourceAllowed` accepts any path containing a `downloads`/`下载` *segment* (e.g. `D:\projects\downloads\...`), looser than the "user Downloads" claim; combined with `use_skill` this forms an ungated .md read chain. Consider binding to homedir/Downloads or Chrome's default.
4. **companion/src/skills/skill-install.ts:123** — content-branch `dest_path: fs.existsSync(dest) ? dest : root` falls back to root — misleading; return the actual written path.

7. **companion/src/server.ts:3244** — `skill_install` (writes to disk + reads Downloads) has no L2 gate, unlike host_write/shell_exec. Surface is bounded and consistent with `record_experience`/`use_skill`, but worth confirming this is intentional.
