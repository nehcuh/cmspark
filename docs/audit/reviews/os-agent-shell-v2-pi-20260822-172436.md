## Findings

### BLOCK
None. Trust laws are enforceable, identity is not a lie (capability vs marketing distinction holds), P0 is landable as a falsification spike.

### MAJOR

**M1 — Overlay "MinimalConfirm" residue: the Sec B2 fold is incomplete in prose/phasing.**
`docs/decisions/os-agent-shell-brief-2026-08-22.md` §5.5 (line 218 "召唤器可以…提供同一 MinimalConfirm"), §9.2.15 (line 291 "Tray 确认与 overlay MinimalConfirm 同时显示"), and **P1 phasing (line 383 "Overlay MinimalConfirm 接入 N5")** all presuppose an overlay confirmation surface — while S6 (line 138) and N2 both lock "MinimalConfirm 仍 Panel-only" and "召唤器…不渲染 Allow/Deny". Every mention is hedged with "观察者 / 单 writer / 不是第二个 writer / 允许显示", so the *security intent* is read-only observer (N5 broadcast fan-out), and an implementer reading S6+S22+S23 has overwhelming signal for no response path. But the term "MinimalConfirm" is the exact name of the Panel-only response chip, and P1 makes it a deliverable — a literal implementer builds an overlay confirm chip, i.e. the exact hole adversary Sec B2 REJECTED v1 for. **Required amendment before spike plan**: rename all three sites to "确认状态徽章（只读 observer，订阅 N5 resolved 广播，无响应路径）"; keep the term MinimalConfirm Panel-only. If the owner intends *any* overlay response path, that is a BLOCK.

### NIT (foldable)

- **N1** — §3 diagram (line 109) labels the summoner "(OS home, L0+search)". The banned word survives as an internal annotation. → "OS 捕获入口".
- **N2** — P2 deliverable (line 391) "「家」的引导" uses the banned word in a user-facing narrative item. → "召唤器入口引导".
- **N3** — §6 table (line ~207) lists `pack.apply` under "召唤器动作" but the same section's prose + S8/S21 hard-reject `allowTrust`/`user_gesture` for overlay origin (verified: `pack.apply` with `user_gesture:true` hardcodes `allowTrust:true`, `message-router.ts:2578`). Table row must read "deep-link Panel" only.
- **N4** — §13 ADR-022 row (line 425) reuses "L9 赢家" for a different concept than ADR-022's L9 (tab-lease). → rename "主叙事赢家（本 brief 语义）".
- **N5** — §9.5.28 (line 308) "接受本 brief 后必须改 GOAL / architecture §0" survived unamended and contradicts S24/§0 freeze. → annotate "经 S24 修订：证伪通过前冻结；P2 再改"。
- **N6** — S19 implementation: `classifyError` defaults non_recoverable, but a sloppy `BROWSER_UNAVAILABLE` message containing "timeout"/"not found"/"disconnected" flips to recoverable → the banned auto-retry. Pin the error text and add an explicit `error_code === "BROWSER_UNAVAILABLE"` non-recoverable guard.
- **N7** — S21's ACL is *new server code* (see verification table). Spike plan must include an origin-class gate table + unit tests; today nothing rejects tray origin at the method layer.
- **N8** — S10 OPEN is acceptable, but P0's own IME 5/5 gate makes the IME×CU process experiment a *de facto* P0 task; it is only in the synthesis ("非激活面板 + 输入时临时 regular"). Name it as an explicit P0 spike task and gate the "临时 regular" fallback against "不截半拼音" (§9.4.22).
- **N9** — P0 task 2 ("问一条不需要网页的问题") is generic chatbot Q&A and weakly tests identity 2. → phrase as "在任务 1 的同一 thread 里追问并引用 hydrate 到的历史内容", so tasks 1+2 jointly test the claim. The strong falsifiers (Chrome-keep-closed, ≥50% open-Chrome, `history.db` zero-auto-L1) do the real work.
- **N10** — overlay-origin `chat.create` is not L0-restricted at the method level: the loop can hit companion-side L2/shell/MCP tools with confirms routed to tray (S6 anticipates this). State it explicitly so "L0 捕获面" isn't misread as capability restriction.
- **N11** — capability declaration "L2 = HUD/Cockpit" could be misread as exclusive; overlay chat can escalate to L2. → "L2 工作面（确认/急停）仍在 HUD/Cockpit/tray"。
