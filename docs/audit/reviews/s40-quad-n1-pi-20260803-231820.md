## Blocking issues — Track 4 shell P1b (companion/src/capability/shell.ts)

**B1 — Windows regression for .cmd/.bat and cmd builtins.** `shellExec` (shell.ts:207–211) now prefers `spawn(argv[0], argv.slice(1), {shell:false})` for **every** parseable command under the default `confirm_per_command` policy. On Windows I verified `spawn('npm', …, {shell:false})` → ENOENT (−4058); `npm`/`npx`/`yarn` are `.cmd` shims, and cmd builtins (`echo`, `dir`, `type`, `copy`) aren't executables either — all previously ran under `shell:true`. There is no `process.platform === "win32"` guard. The existing test `shell_exec runs when enabled` (capability-shell-netsec.test.ts:38) passes only because this dev box has Git Bash's `/usr/bin/echo.exe` on PATH (verified) — it would ENOENT on a stock Windows install, so CI here cannot catch the breakage.

**B2 — Quoted Windows paths are corrupted; executed argv ≠ confirmed command.** `tryParseSimpleArgv` treats `\` as an escape inside quotes (shell.ts:143–147), which is POSIX semantics, wrong for Windows paths. Verified: `python "C:\Users\t\script.py" --flag` → `["python","C:Users\tscript.py","--flag"]`. Legit commands ENOENT, and the L2-confirmed command string diverges from the argv actually spawned — a confirmed-vs-executed integrity gap, untested for win32 spawn behavior.
