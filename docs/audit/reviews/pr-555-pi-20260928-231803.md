## BLOCKING（必须修才能合）

- **[P0] `chrome-extension/src/background/browser-bridge.ts:1621` + `companion/src/security.ts:1083-1111` — 新错误码 `WAIT_PROBE_FAILED` 未注册，会把「修复前 recoverable 的瞬时故障」变成 `non_recoverable` → 整轮 `security_halt`。**
  我在**真实执行链**上复现（不是单点调 `classifyError`）：stub 让 attach 成功、`sendCommand("Runtime.evaluate")` 抛 `No target with given id`、`executeScript` 抛 `The extensions gallery cannot be scripted.`，跑 `bridge.execute("wait_for", {timeout:8000, interval:30})`：
  ```
  error : WAIT_PROBE_FAILED: selector probe failed on both channels — cdp: No target with given id; scripting: scripting selector probe failed in ISOLATED and MAIN worlds
  data  : {"error_code":"WAIT_PROBE_FAILED","suggested_action":"list_tabs","tab_url":"https://chromewebstore.google.com/..."}
  classifyError -> non_recoverable
  ```
  触发条件：CDP 失败发生在 **post-attach 的 `sendCommand`**（`ensureAttached` 自己的失败会被包装成 "Debugger attach failed" → 命中正则，走 `CDP_ATTACH_FAILED`，没事），且合并消息里没有 `debugger|not attached|attach failed|cannot access|script injection|inspected target|target closed|chrome://|…` 任一 token（`locator-classify.ts:79-83`），URL 又非 privileged → 落到 fallback `WAIT_PROBE_FAILED`。我实测其他会命中的形态：`Detached while handling command.` + webstore、`Frame with ID 0 is showing error page`、`The tab was closed.`（组合里同样缺 token 时）。
  后果：`adapter.ts:2121-2152` 收到 `non_recoverable` 即 `shouldStop = true; terminal = "security_halt"` → `break`，整轮对话被「不可恢复错误」终止；而**修复前**同场景是空转到 deadline 后报 `Timeout waiting for selector…` → recoverable → 模型换路/重试。这与 `suggested_action: "list_tabs"`（要求模型换路）自相矛盾。
  该 code 还违反仓库自设不变量：`companion/src/security.ts:1083` 注明「Web act-loop W1/W3′/W4 coded errors (default is non_recoverable)」，`companion/tests/web-act-loop-wave1.test.ts:46-61` 专门钉住这族码必须 recoverable。我把 `"WAIT_PROBE_FAILED: selector probe failed on both channels"` 加进那张表，**该测试立刻变红**（`AssertionError: WAIT_PROBE_FAILED: selector probe failed on both channels`）——说明这是遗漏，不是设计。
  附带影响：`site-op-memory.ts:72` 的 `ATTACH_CODES = {CDP_ATTACH_FAILED, WRONG_ORIGIN}` 是 tab attach-freeze 的入口；新 code 既冻结不了 tab，又把一次**传输层**故障记进 origin 交互失败计数（`originEscalateDue`）→ 4 次后升级到 host_computer 建议。真实原因是「没有通道能读 DOM」，code 却由消息文本决定。
  修法（一行级）：把 `wait_probe_failed` 加进 `companion/src/security.ts` 的 recoverable 列表并补进 `web-act-loop-wave1.test.ts` 的表；或直接传更准确的码（`CDP_ATTACH_FAILED`）以复用既有 recoverable + freeze 语义。

- **[P1] `chrome-extension/src/background/browser-bridge.ts:1596-1618`（+ `:58-64` 注释，+ commit body「瞬时故障（页面导航中）不再中断等待」）— 用「轮数」而不是「时间/deadline」做失败预算，实测**提前放弃**了 main 上本来会成功的等待。**
  同一脚本、同一 chrome stub，只换 bridge 源码（`main` vs 本分支），场景：两个通道在 HEAL 前都不可用、之后恢复正常（慢导航/attach 竞态），调用方要求 `timeout: 8000, interval: 500`：
  ```
  NEW  heal=1200ms → elapsed=1014ms success=false code=CDP_ATTACH_FAILED
  NEW  heal=2000ms → elapsed=1027ms success=false code=CDP_ATTACH_FAILED
  NEW  heal=4000ms → elapsed=1024ms success=false code=CDP_ATTACH_FAILED
  OLD  heal=1200ms → elapsed=1509ms success=true
  OLD  heal=2000ms → elapsed=2021ms success=true
  OLD  heal=4000ms → elapsed=4029ms success=true
  ```
  即容错窗口从「整个 deadline（15s 默认）」缩到 `2×interval ≈ 1s`，且**预算随调用方传的 `interval` 缩放**（`interval:50` → 约 100ms 容错）。注释声称「keeps a transient blip (tab mid-navigation) from aborting the wait」，实测恰恰在导航中放弃——注释与实现相反，属未声明的能力回归（`wait_for` 不再等价地「等到 deadline」）。
  同一设计还留下**反向**漏洞：当 `timeout ≤ ~2–3×interval` 时 3 次失败塞不进 deadline，循环带着 `probeFailure === null` 退出 → 又报假的 `WAIT_TIMEOUT`（实测 `timeout=1000, interval=500`，两通道全死 → `WAIT_TIMEOUT: timeout after 1000ms waiting for selector "#app" to be visible`；`timeout=300, interval=100` → 正常走 `CDP_ATTACH_FAILED`）。这正是 #554 要消灭的归因错误，只是缩到了边界配置。
  推荐统一修法：保留「重试到 deadline」，但累计 `lastProbeError` 与 `anyProbeSucceeded`；deadline 到点且**从未有任何一轮探测成功**时走 `failInteractive(lastProbeError)`，否则才是真超时。这样既保住 main 的等待能力，又保住本次修复的「不冒充元素缺失」目标；若坚持快速失败，预算应按 `timeout` 派生（如 `max(2s, min(timeout/2, 5s))`）而不是按轮数。
  （诚实标注：机制在 stub 上确证；**真实 Chrome 里「两通道同时死 >1s」的发生频率我无法在本沙箱实测**。若团队判断该窗口可接受，请至少修正 `:58-64` 与 commit body 的相反表述，并把它降级为 nit。）
