### Non-blocking observations beyond the report's N1 (not grounds for rejection)

1. **ODF budgets are a hard import floor, not only a bomb defence.** `MAX_NODES=100_000` is cumulative per document (`odf-expansion.ts:22,36,88`), so ~33k populated cells is the practical ceiling: measured 100×100 cells **admitted**, 200×300 cells and a 10 000-row × 6-column cell block **refused** (`展开节点`). An `.odt` with a large table that used to parse is now refused. It is an honest, documented ("ODF budgets", split/save-as) refusal, so not a blocker — but the README quotes no threshold, and saving as XLSX avoids the guard entirely.
2. **The guard refuses on xmldom *warnings* too** (`odf-expansion.ts:200` `onError: () => refuse("XML 损坏")`), e.g. U+FFFD from any non-UTF-8 byte or an unquoted attribute (`@xmldom/xmldom/lib/sax.js:52,347,363,417`), where `officeparser`'s `parseXmlString` (`xmlUtils.js`) tolerates them. Fail-closed; broadens the "malformed" class.
3. **`chartCost` returns zero for the main `content.xml`/`styles.xml`** (`odf-expansion.ts:110`). Correct only because upstream extracts charts solely from entries matching `Object \d+/content\.xml` (`OpenOfficeParser.js:1517-1531`) and the frame branch's `objectPath`/`endsWith` resolution never matches the main entry. Deliberate, but a coupling worth a comment.
4. **Removal of the old tmp-dir containment assertion** (old `file-parser.ts` resolved-path check → new `input.${sourceExt}` at `file-parser.ts:227`). I probed this as a possible arbitrary-write regression: `documentExtension` returns the substring after the **last** dot, which is dot-free, so no `..` segment can appear; a leading `/` is absorbed by the literal `input.` prefix (`path.join(tmp,'input.'+'/x')` stays inside). Verified with Node `path.join`; **not exploitable**, so not a blocker — but the explicit guard was replaced by an implicit invariant.
5. **A config whose normalized set exactly equals the legacy default is silently upgraded** (`file-formats.ts:54-60`), including a user who deliberately re-entered exactly that ten-MIME set. The file is not rewritten and the report calls this out as intended; noting it as a minor trust nuance only.
