### Blocking issue — Track 4 win32 `.bat`/`.cmd` regression (incomplete B1 fix)

N1 flagged "Windows regression for .cmd/.bat". The N1B fix handles bare names (`npm`, `echo`, `dir` keep `shell:true`) but **explicitly routes extension-bearing `.bat`/`.cmd` programs into argv mode**:

- `companion/src/capability/shell.ts:183` — `/\.(exe|com|bat|cmd)$/i.test(prog)` → argv mode, with docstring claiming `.bat/.cmd` are "explicit executable path" candidates.
- Empirically verified on this box (Node v24, win32): `spawn('C:\\x\\setup.bat', ['--flag'], {shell:false})` throws **synchronously EINVAL** — not an async `error` event. `shellExec` (shell.ts:242) has no try/catch around `spawn`, so every `.bat`/`.cmd` command (e.g. `venv\Scripts\activate.bat`, a downloaded `setup.bat --silent`) that ran fine pre-P1b via `shell:true` now returns `{success:false, error:"spawn EINVAL"}`.
- `companion/src/capability/shell.ts:181` — win32 `policy=allowlist` routes *any* parsed command to argv mode, so allowlisted `npm run build` (a `.cmd` shim) → ENOENT; previously worked via shell.
- Tests (`shell-progress-windowsHide.test.ts`) only assert the *decision function* (`shouldUseArgvSpawn`), never an actual win32 spawn — so the synchronous EINVAL regression is invisible to CI.

This is the same regression class N1 rejected, only partially fixed, and the code comment states a claim that is factually wrong on Node/win32. Not a security escalation (argv mode is fail-closed; the error is caught upstream at server.ts:2242), but it is a functional regression on the primary platform with an incorrect "safe" claim — failing the "reject if incomplete claims" bar.
