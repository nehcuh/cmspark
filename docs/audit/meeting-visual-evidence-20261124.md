# 会议录屏画面证据验收

在 Windows 本机使用 Chrome 157 和 LM Studio 的 `google/gemma-4-12b-qat`，比较了同一份中文逐字稿的纯文字纪要和带画面证据的纪要。画面来自专用的合成会议标签页。逐字稿由夹具固定，以便两组逐字比较。音频转写质量另见 [Windows 本机转写验收](windows-voice-gpu-20261123.md)。

## 录制与识别

Chrome 实际打开所选标签页的显示轨道，经产品录制、变化采样和 IndexedDB 存储，生成 WebM 和三张 1280 × 720 JPEG。第一张显示 A 方案 18 万、B 方案 23 万；手动标记记录了 B 改为 24 万；第三张自动保留代码演示。代码包含 `retryLimit = 4`、`timeoutMs = 750` 和预览状态。口头材料只谈到预估二十万元、预算待核对，且没有批准发布。

录制结束后通过会议组件预览所选截图和相邻转写，再确认接收方。三张原图共 142,016 字节。计数代理记录五次模型请求，依次是纯文字纪要、三次单图识别、增强文字纪要。确认前的图片请求数为零。真实图像模型读出两版预算、代码中的数值和预览状态。纪要的画面引用可以打开对应 JPEG 和本地 WebM 播放器。

复验使用独立的 Companion 数据目录。浏览器夹具用适配器连接实际消息校验、会议处理器与后台中继，模型请求由仅监听回环地址的计数代理转发。扩展连接身份、配对边界、断线和取消另有协议回归。

| 同一逐字稿的实际输出 | 纯文字 | 加入三张画面证据 |
| --- | --- | --- |
| 口头估算与屏幕预算 | 只记录口头讨论 | 将二十万与屏幕 B 方案 24 万的差异列入开放问题，同时引用发言和表格 |
| 预算及代码 | 没有画面数值 | 记录 A 的 18 万／12 周、B 的 24 万／8 周，以及重试 4 次、超时 750 ms，三张截图均被引用 |
| 将草案列作已批准决议 | 0 条 | 0 条 |
| 模型端耗时 | 39.975 秒 | 三图识别端到端 9.11 秒，随后文字生成 5.025 秒 |

三次含图的 HTTP 请求体合计 192,639 字节，包含编码后的图片、提示和相邻转写。本次摘要记录了最终预算，没有复述 B 方案原先的 23 万，也没有单独摘录预览状态；两项原始识别都保留在对应画面证据中。这些结果来自两段受控会议，不是对真实会议总体准确率的估计。

## 采样覆盖

- 单个数字 1307 改为 1308 时，实浏览器在首帧后 60.508 秒的兜底检查保留第二帧。之后回到旧画面并手动标记，内容哈希去重生效。
- 180 毫秒的过渡页未留存。录屏仍可回看全段；稀疏截图适于核对稳定画面，无法还原每个点击或动画步骤。
- 关闭留存时仍能生成录屏与音频，截图数为零。原数据库升级及删除录制后读取旧截图的回归均经过实际 IndexedDB。

## 图表与快速滚动

另一段 15.912 秒的录像先展示折线图，随后快速滚动代码。逐字稿仅有“现在一起看这页材料，再看看软件演示”。折线图的数据点没有数值标注。全程使用自动采样，模型从坐标轴读出四个季度的 10、30、20、40，并识别出先升、后降、再升的趋势。连续滚动 6.841 秒期间没有保存中间帧，停止后 1.602 秒留下的代码画面包含 `queueLimit=17`、`flushMs=420` 和 `mode=preview`，三个字段均识别正确。两张原图合计 60,302 字节，确认前请求数为零，确认后逐张发送，批次实耗 5.36 秒。

浏览器回归入口为 [桌面录制集成测试](../../chrome-extension/scripts/test-desktop-meeting-mix.py)。接收方确认、请求期限与证据持久化见 [Companion 视觉处理测试](../../companion/tests/meeting-visual.test.ts)。文字与画面来源、失效和删除见 [纪要回归](../../companion/tests/meeting-visual-minutes.test.ts)。
