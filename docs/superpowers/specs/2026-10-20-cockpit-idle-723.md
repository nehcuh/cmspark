# Authoritative idle cockpit collapse

GitHub: #723
Status: implemented candidate; two nonauthor reviews and remote browser acceptance pending. Development version 0.6.14; partial #723 only.

An authenticated extension-panel peer may ask `cockpit.idle.get` with the existing bounded request `id`. Only the same currently authenticated WS receives `cockpit.idle.result` with that id and the closed `IDLE|BUSY|UNKNOWN` state. This is a root-approved coarse installation activity observation; it discloses no count, owner/confirmation/task ID, text or secret, and grants no authority.

The server synchronously reads the actual singleton confirmation pending count and global active computer-task registry, then queues the reply without an await. Any pending confirmation, including another owner's or unbound/fanout request, or any registered task (including aborting) is BUSY. Missing/invalid authority is UNKNOWN. Other authenticated surfaces are not eligible. This observes a moment and preserves earlier queued-frame order; it is not a reservation or completion barrier for arbitrary async work.

The client keeps at most one socket/generation-bound query/receipt, without preauth buffering, polling or retry. Connection/auth loss/error, relevant confirmation/task events and explicit window actions invalidate it. A malformed/error reply is UNKNOWN. No receipt changes the confirmation queue or task state. Recovered empty UI mirrors are insufficient by themselves.

After a resolved/expired confirmation or finished task, automatic collapse additionally requires local pending0 and task absent/finished, the same current lifecycle, and a populated popup containing exactly the extension cockpit tab (origin/path, never title). Every asynchronous observation must still belong to that lifecycle/idle intent. The final receipt/connection/mirror/owner check and remove dispatch share one JS turn. Storage writes remain ordered and their late completions never mutate newer ownership. Explicit close does not abort a task.

Chrome remove cannot be revoked. A new still-current original #326 open_focus intent waits for actual removal, then uses existing open/focus behavior; light stay_background requests remain on their original surfaces. A brief close/reopen is allowed, not hidden by a zero-gap promise. Unknown remove outcome keeps the known owner for revalidation. No task/confirmation is approved or cancelled by window lifecycle.

No L2/45s, dialog threshold/channel, original capture protection, quality/rect or ADR-017 changes. CPU scheduling controls are not real Chrome/Win32 visibility proof. Whole #723 remains partial.
