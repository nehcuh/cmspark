# #533 current conversation site failure counter

Existing issue #533 requests visible settings status/reset, which current code lacks. Current failure counts are already per-thread, not durable cross-thread counters; #535 known-channel locator experience is a distinct layer and its frozen source is preserved.

Add a UI-only settings command through authenticated extension WS, not an LLM tool. Bind current selected thread to its actual authenticated connection; derive HTTP(S) exact origin and current active tab through trusted metadata invocation options. Status exposes only origin, count, fixed registered code/UNKNOWN, existing threshold4, boolean locator/attachment layers and unknown health. Explicit human reset touches only the current origin runtime count, preserves last code/UNKNOWN, locator/history/attachment/grants/nonces/profile and other scopes, and never implies READY.

Use smallest authoritative busy refusal: active LLM controller, pending owned tools or human confirmation refuse reset. Recheck owner/socket/thread, active tab/target after each metadata await; perform final busy check and synchronous count mutation without another await. A refused reset must show failure; no automatic retry or generation reset framework. Current browser metadata is a bounded observation, not an atomic lock on future Chrome navigation or a grant.

Reset uses the current selection's last server-produced target receipt. A new selection or status receipt observed during an await invalidates the old reset attempt. The runtime sender must be this extension's top-frame sidepanel page; the UI's request never chooses a hostname or tab. Browser forwarding acknowledges the selected tab but does not complete the operation. The UI settles only the corresponding server reply, including the acknowledged tab, thread, request ID and operation kind; it clears stale views after navigation, owner change or disconnection and reports bounded transport/response failure without an automatic decision retry.

The view also binds pending responses and cleanup to the existing canonical `activeThreadSelectionRevision`. Distinct explicit selection actions invalidate an earlier view even when React batches A → B → A into one final-A render. Ordinary rerenders keep this revision and valid requests intact. This is UI ownership only: it does not change backend counter generations, authority, counts or operation receipts. Permanent actual-App controls cover legitimate unchanged-owner success/refusal, ordinary rerender, separate/batched return, null selection and stale success/refusal; recordings retain genuine producer semantics with declared synthetic transport timing.

Prove actual router/validator/read producer plus settings/SW/UI replies, active/pending/confirmation refusal and late owner/tab/navigation/disconnect negatives.
