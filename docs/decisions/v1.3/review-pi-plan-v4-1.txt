SCRUTINY: 6 SPECIFIC POINTS
================================================================================

(1) Luma stdev < 1.0 threshold — empirically defensible?
    PARTIALLY. The threshold is reasonable for the failure class it
    targets (SCK returning a fully black frame for an occluded
    background window). Concerns:
      - False positive: a terminal showing a solid black background
        with a blinking caret has high stdev (caret pixels are
        bright) — false positive risk is LOW for terminals.
      - False positive: an image viewer showing a full-screen white
        or black photo. Stdev = 0 → wrongly classified stale.
        Mitigation: the OR with the 99% identity check does NOT
        help here because a freshly-launched image viewer has no
        prior capture to compare against. AND-OR logic must be:
        fail-closed ONLY when BOTH (stdev < 1.0) AND (identity
        with prior same-windowId ≥ 99%); if there is no prior, fall
        back to (stdev < 1.0) AND (window reports non-trivial
        bounds). Claude must implement the no-prior case correctly.
      - Recommendation: combine as "(stdev < 1.0) AND (no-prior OR
        identity_with_prior ≥ 99%)" — i.e. both conditions
        informational, fail-closed when the simpler test triggers
        without contradicting evidence. OR (Grok's wording) is too
        permissive: a stale frame with caret blink could miss the
        stdev test but match identity.

    CAVEAT (Claude must honor): use AND-of-conditions when a prior
    exists; use stdev-only when no prior exists. Document the
    decision in code.

(2) 64x64 downsample for identity check — resolution sufficient?
    YES, with caveat. A 64x64 grid on a 1440x900 capture = ~22x14
    pixel cells. This catches:
      - Window-level changes (any window movement, resize, occlusion
        change): YES — at least one cell flips.
      - Caret blink: A single 1-2px caret line falls within ONE cell;
        flipping that cell changes 1/4096 cells = 0.024% — WELL below
        the 99% identity threshold (i.e. identity = 99.976%). So
        caret blink does NOT trigger a false "stale" classification.
      - Hover state transitions: typically change a button-sized
        region (~30x15 px) = at least one cell. Triggers correctly.
    False-negative rate for typical UI animations: < 1%.
    Caveat: the 99% identity threshold means "at most 1% of cells
    changed" = "at most 40 cells of 4096 changed". That is generous.
    Claude should consider tighter (e.g. 99.9% = max 4 cells) once
    canary data exists. For v4.1 ship, 99% is acceptable.

(3) reL2ShouldPrompt(tags) unknown-tag fail-closed — strict enough?
    YES. Unknown-tag fail-closed means "prompt" (the safe default).
    Test for tag exhaustiveness: Claude MUST add a unit test that
    enumerates every reason string used in `reL2(...)` call sites
    (today: budget_exhausted, uncrossverified_exceeded, self_ui_yield,
    dialog_suspected, danger_detected, experimental_suggestion,
    foreground_yielded-non-self-ui — verify against actual call
    sites at executor.ts:636+). The unit test must assert that
    every emitted reason is classified as silent or prompt-always,
    never unknown. A CI run with a new reason that the predicate
    doesn't know about must FAIL the suite, not silently pass.

    CAVEAT (Claude must honor): implement the test as
    `for reason of ALL_REASONS: expect(classification).toBeDefined()`
    against a hardcoded ALL_REASONS array updated when adding a
    reason. Do NOT rely on type-level exhaustiveness — TypeScript
    doesn't enforce this at the emit site.

(4) credentialSurfaceSeen latch source — reliable?
    SEE D3.2 above. Pipeline exists and is reliable (Vision OCR
    is the same path that already gates the hard-deny at
    executor.ts:893). Reliability is sufficient for a safety latch
    because the failure mode is fail-closed drop (executor.ts:1213-
    1218). The CAVEAT for Claude: when afterOcr === null, set the
    latch to TRUE (defensive) — do not silently skip the latch on
    OCR failure.

(5) 30 min idle expiry — threat-modeled or round number?
    ROUND NUMBER with weak threat-model backing. 30 min is a UX
    compromise, not derived from a specific threat. Threat axes:
      - Shoulder-surfing during stepped-away session: 5-10 min
        would be tighter (screen lock default on macOS is 5 min).
      - Prompt-injection window after user left: bounded by
        session-trust grant lifetime; 30 min is generous.
      - Cost of false re-prompt after idle: low (one extra click).
    Verdict: 30 min is acceptable; tighter (10-15 min) would be
    defensible. NOT a blocker — Claude may ship 30 min default
    but should make it configurable (already implied by "default").

(6) Gate verification (D3.3) — Grok's claim that server.ts:2078 is
    NOT a second L2 gate.
    INDEPENDENTLY VERIFIED BY PI. See D3.3 above.
    server.ts:2078 is the `case "host_computer":` block in the
    post-token-execute switch. It validates the security token at
    :2082-2091 and the single-task invariant at :2107-2114. It does
    NOT consult ComputerSessionTrust and does NOT show a dialog.
    Grok's claim is correct. T2 silent-skip design has no hole from
    a missed gate.
