## Answers

### 1. C3 static gate

**Keep the static flag + `activeInstance`.** Your reasoning is right: latest instance wins, production singleton is unchanged, `close()` already flushes that instance. Unregister-on-close is more bug-prone (need re-arm on next construct) and not better for the production shape.

Optional polish only: clear `activeInstance` when `close()` closes the current one. Harmless today (`flushNow` on a drained closed store is a no-op).

### 2. C5 resolve semantics

**`{ id, approved: false }` is correct.** Do not add a `cancelled` sentinel now.

Cancel-due-to-other-channel is operationally a deny for the tray channel; the race winner is always WS (or tray if tray won first). No production path branches on user-deny vs cancel. A sentinel would churn types for zero callers. If you want metrics later, log at the `server.ts` cancel call site instead.

### 3. Anything else?

**Nothing that re-opens Round 1.** Residual nits are opportunistic. Frame C-P0-1 in the PR as “serialization primitive landed,” not “race fixed.”
ore.activeInstance?.flushNow()` → latest live store.
- After instance #1 `close()` flushes, then #2 is constructed, #2 is `activeInstance` and receives the final flush. Good.

Why not prefer unregister-in-close as the primary design:

- `process.once` listeners are harder to remove cleanly without storing the exact function refs; re-registering on every construct reintroduces the original leak under test churn.
- Static install-once + pointer indirection is the standard “singleton resource, multi-instance tests” pattern.
- `close()` already calls `flushNow()` for the instance being closed, so durability does not depend on the process handlers for the normal test lifecycle.

Optional polish (nit, not a concern):

```ts
close(): void {
  this.flushNow()
  if (HistoryStore.activeInstance === this) {
    HistoryStore.activeInstance = null
  }
  // ...
}
```

That avoids a closed instance remaining as the shutdown target until the next ctor. Harmless today (`flushNow` on a closed store with `pendingSinceFlush === 0` is a no-op), but clearer ownership. Do not unregister process handlers on close unless you also re-arm them on next construct — that path is more bug-prone than the static gate.

### 2. C5 resolve semantics: `approved: false` vs `cancelled: true`

**`{ id, approved: false }` is the right choice. Do not introduce a cancelled sentinel now.**

Reasons:

1. **Current consumers.** `server.ts` races tray vs WS. When WS wins, it calls `cancelConfirm` and returns the WS decision; nobody further awaits `trayPromise`. The cancel resolve is purely anti-hang for future direct `await trayPromise`.
2. **Semantic fit.** Cancel-due-to-other-channel is operationally a deny for the tray channel: the dialog should close, no approve side effects, and any late Swift reply is already dropped because the map entry was deleted first. That matches timeout and user-deny as fail-closed for that channel.
3. **Cost of a sentinel.** A distinct `cancelled: true` (or `reason: "cancelled"`) requires typing changes on `TrayConfirmResponse`, adapter surface, and every consumer that currently treats the response as binary. No production path needs to branch on “user deny vs cancel” today; the race winner is always the other channel.
4. **Double-settle safety.** Order is delete map → resolve false → send cancel-confirm. Late `confirm-response` from Swift sees no entry. No double-resolve into `SecurityConfirmationManager` because cancel only settles the *tray* Promise, not the manager.

If you ever need metrics (“how often did Side Panel win vs tray?”), log at the cancel call site in `server.ts` (`security.confirmation.tray_cancelled_after_ws_win`) rather than expanding the response type.
