## Tab lock model

States per tabId: FREE | SOFT_RESERVED(holder,confirm_id,deadline≤45s) | HARD_HELD(holder,renewed_at,idle_ttl,hard_max_deadline) | FORCE_RELEASING. Transitions: FREE --createToolExecutor resolves tabId & holder check--> HARD_HELD (no L2 path) OR SOFT_RESERVED (L2 path, intent only, non-blocking to other SOFT). SOFT_RESERVED --user approve--> hard re-acquire: if still free-or-same-holder → HARD_HELD else TAB_LOCKED post-confirm (recoverable). SOFT_RESERVED --deny|timeout|rejectAll|disconnect--> FREE. HARD_HELD --same-holder tab-tool entry--> renew (reset idle). HARD_HELD --idle_ttl|hard_max--> FREE + audit LEASE_EXPIRED. HARD_HELD --holder handback|worker-cancel|chat.abort(holder)|close_tab success--> FREE. HARD_HELD --Dashboard force-release (originWs, explicit)--> FORCE_RELEASING → FREE + audit. HARD_HELD --other thread any tab-targeted tool--> refuse TAB_LOCKED (no queue-steal). Unit=tabId(number); holder=worker thread_id; run_id never holds. Gate=Companion createToolExecutor after normalize/resolve, before L2 and immediately again before ws tool.execute; Extension queue optional P1. Scope=all tab-targeted tools P0 incl. pure reads; list_tabs/create_tab/cookies/host_*/shell/netsec exempt. osascript_eval: hard-resolve URL to unique tabId or TAB_AMBIGUOUS/deny for workers. Multi-tab: lazy acquire up to per-worker cap. Abort/cancel must reject holder pendingToolCalls then release. Invariant: ∀ tabId, |exclusive holders| ≤ 1.

## Open questions

- Default numeric caps: max concurrent workers per orchestrator_run, process-wide max LLM loops, per-worker max simultaneous tab leases, idle_ttl and hard_max lease durations — product/cost call (engineering proposes defaults; user signs).
- P0 pure-read exclusivity vs later shared-observer: keep exclusive-for-all through first ship, or allow read-only shared mode in P1 for screenshot/get_page_* while mutate stays exclusive?
- Worker evaluate policy: permanent WORKER_HARD_DENY unless elevation grant, or pack-scoped allow for trusted community packs without full elevation?
- host_computer that targets a coordinate-allowed Chrome window can mutate page content without tabId — product rule: forbid host_computer against Chrome while any tab lease exists, require force-release first, or accept as separate host risk surface?
- Soft reservation exclusivity: should SOFT_RESERVED block other workers' soft intents (early busy), or only HARD_HELD blocks (post-L2 TAB_LOCKED risk after user already confirmed)?
- Dashboard placement: extend existing Cockpit shell vs sibling chrome.windows fleet window (confirm-storm / single L2 center UX).

## Rejected alternatives

- Prompt-only / honor-system tab locks ("please don't touch that tab") — fails H3 under concurrent workers; no createToolExecutor gate.
- Per-tool-only lock scoped to pendingToolCalls RTT — legal interleave between tool.result and next holder dispatch; violates multi-tool episode exclusivity.
- Extension-only locking (BrowserBridge queue sole authority) — dual-layer A1 violated; Companion can still multi-dispatch; L2/confirm races unsolved.
- Holding exclusive HARD lease across full 45s L2 confirmation wait — deadlocks multi-worker evaluate/navigate; strands locks on rejectAll/disconnect.
- Silent parallel shell_exec/netsec_port_scan across workers (or skip L2 via whitelist/auto_approve) — brief non-goal; weaker than host_computer single-flight.
- Null worker tool_whitelist (= allow-all today) or orchestrator with full browser+host tools by default — capability theater; isToolAllowed unused would let invented tools run under L2 only.
- pinned_tabs as exclusive ownership / lock grant — reifies multi-thread pin collisions as fake ownership; affinity only.
- Orchestrator run_id as tab lock holder for workers, or free in-process swarm outside ThreadManager — breaks HITL enter-worker, abort, audit, pack composition.
- Dashboard/broadcast approve API or unbinding respondFrom originWs — C-SEC-2 cross-client approve; whitelist injection risk.
- Merging tab lease registry with host_computer computerTaskAbort — false busy, wrong cancel UX; host tools have no tabId lock domain.

## Survivors (verified sound)

### TAB_LOCK-3 (must / TAB_LOCK)

Lock is a multi-tool lease for the holder's operating episode, not only a single pendingToolCalls RTT: auto-renew on each holder tab-tool dispatch; idle timeout after last renew; hard max lease then auto-release+audit; explicit release on worker turn/done, holder chat.abort, or tab close. Per-tool-only locking is insufficient for the hard rule.

- reason: Multi-tool episode lease is required for the hard exclusive-tab rule: browser ops are discrete tools (click/type/fill_form/navigate), and pendingToolCalls only covers a single RTT, so per-tool locks leave a legal interleave window between tool.result and the next holder dispatch. Companion-side lease map in createToolExecutor (with renew on holder tab-tool entry, before L2) is real enforcement—same class as host_computer COMPUTER_TASK_BUSY—not honor-system prompts. Per-tab (not global browser) preserves multi-agent parallelism. Release hooks map to existing abortControllers (chat.abort), close_tab success path, and idle/hard-max deadman timers. Compatible with dual-layer topology and does not bypass L2 if gate/renew precede confirmation.

### ORCHESTRATOR_WORKER_MODEL-2 (must / ORCHESTRATOR_WORKER_MODEL)

The orchestrator Thread MUST run with a hard narrow tool surface by default: spawn/wait/collect/ask_user (and read-only status: list_workers, get_worker_status) only — no browser mutate tools (click/type/navigate/evaluate), no shell_exec/netsec/host_computer/osascript_eval, unless the user explicitly elevates that orchestrator after a separate confirm.

- reason: Must-rule is product-correct and implementable on existing Companion Thread primitives. ### TAB_LOCK-1

Exclusive lock unit is Chrome tabId (number) only—not window, profile, or whole CDP. Holder is the worker's thread_id; orchestrator run_id authorizes spawn but does not hold tab locks for workers. One tab has at most one exclusive holder; a worker may hold multiple tab locks.

- why unsound: TAB_LOCK-1’s unit/holder choice matches the codebase (mutate tools and getTabId/tabId normalize are tab-scoped; pinned_tabs is soft and collides across concurrent threads; worker thread_id is the right holder for HITL enter-worker).
